# Windows-дистрибутив — 0.11.0

## Установка и переход с Python

1. Закрой Director Calendar, включая прежний запуск из папки исходников.
2. Открой Actions → Windows distribution → успешный запуск для нужного коммита → артефакт DirectorCalendar-Windows-x64. Распакуй скачанный архив.
3. Запусти DirectorCalendar-0.11.0-Setup-x64.exe от своего обычного пользователя. Python, PowerShell и права администратора для работы приложения не нужны.
4. Открой ярлык Director Calendar. Установщик обновляет одноимённый ярлык рабочего стола и добавляет ярлык меню «Пуск».
5. Проверь привычные события, историю и настройки. Если использовалась стандартная папка данных, ничего переносить не надо.

Файлы программы: `%LOCALAPPDATA%\Programs\DirectorCalendar`.
Данные: `%LOCALAPPDATA%\DirectorControl\director_control.db`.
Это разные папки. Установка/обновление/удаление программы не удаляют базу и резервные копии. Пароль хранится отдельно в Windows Credential Manager с прежним именем сервиса `DirectorControl.CalDAV` и прежним ключом календаря.

Если раньше использовался `DIRECTOR_CONTROL_DATA_DIR`, сохрани эту переменную окружения для нового запуска: нестандартная база автоматически не угадывается. При смене Windows-пользователя/ПК пароль Vault не переносится вместе с SQLite; его нужно ввести заново.

## Обновление

Закрой приложение, запусти установщик следующей версии и открой прежний ярлык. Автоматического скачивания обновлений пока нет. Скачивать следует артефакт своего приватного репозитория с успешными проверками.

Перед первым открытием существующей базы другой версией приложение под блокировкой одного экземпляра проверяет её и создаёт `backups/before-update-*.db`. Только после успешной копии допускаются инициализация/миграции. Если места нет или копия не проходит проверку, запуск останавливается; исходная база не заменяется. После успешного создания окна сохраняется номер версии в настройках. Повторные запуски той же версии не создают повторных копий обновления. Страховочные копии не удаляются автоматической ротацией.

Установщик блокирует установку/удаление при работающей версии 0.11.0+; старая 0.10.0 ещё не создаёт installer mutex, поэтому перед первой установкой обязательно закрыть её вручную. Имеющаяся блокировка БД по-прежнему защищает от двух экземпляров, включая запуск из исходников.

Понижение установленной версии блокируется. Новая программа также отказывается открывать базу с более новым сохранённым номером приложения. Это не защита от запуска старого исходного кода, не знающего этого правила. Для аварийного возврата используй проверенную резервную копию и соответствующую ей версию, сохранив отдельно актуальную базу. Автоматический откат приложения/базы не реализован.

## Переносимая поставка

Распакуй **весь** `DirectorCalendar-0.11.0-portable-x64.zip`, сохрани рядом `DirectorCalendar.exe` и каталог `_internal`. Запусти exe; при необходимости создай ярлык из настроек приложения. Данные всё равно хранятся в AppData, а не рядом с exe. Для обновления распакуй новую версию в отдельную папку и обнови ярлык. Не копируй только exe и не накладывай разные версии `_internal` вручную.

## Что проверяет CI

- Реальная сборка оконного exe с включёнными Python/Qt, иконкой, tzdata, сертификатами TLS и Windows Vault backend.
- Сборка предыдущих исходников `a7e5242` (0.10.0) тем же упаковщиком — не переименование версии нового exe.
- Создание синтетических данных старым Store, запуск старого установленного exe, установка нового поверх него и повторный запуск.
- Сравнение таблиц событий, исходного плана, факта, истории, категорий, настроек; только служебные отметки версии/автокопии могут изменяться.
- Страховочная копия перед первым новым запуском; отсутствие дублирования при переустановке.
- Сохранение синтетического пароля в Windows Vault.
- Путь с кириллицей, пробелами, апострофом и `&`; запуск из сторонней папки, без Python в PATH/PYTHONPATH/PYTHONHOME.
- Блокировка обновления работающего приложения и downgrade; сохранность базы/копий/Vault после удаления и новой установки.
- Диагностика самого bundle: GUI, iCalendar, часовой пояс, CA bundle, Vault, backup/restore и путь ярлыка.

`--verify-installation <result.json>` — явная диагностическая команда для разработчика. Она использует временную синтетическую базу, отдельную временную запись Vault и не открывает рабочий календарь. Сетевого доступа к Mail.ru нет.

Hosted Windows runner всё ещё содержит установленный Python, но дочернему exe недоступны пути к нему. Это сильная проверка автономности, не замена приёмки на чистой Windows 10/11 и реальном Mail.ru. Дистрибутив пока не подписан Authenticode; сертификат подписи не настроен. Версия 1.0 не выпускается.

## Воспроизводимая процедура сборки

Windows x64, Python 3.13 x64 и Inno Setup **6.7.1**:

```powershell
./scripts/build_windows.ps1
```

Зависимости runtime и сборки закреплены точными версиями в `packaging/requirements-windows.lock`; установка идёт без автоматического выбора транзитивных зависимостей, затем `pip check` проверяет полноту. `.build-venv` отделён от рабочего окружения `.venv`. Конфигурация PyInstaller — `packaging/director-calendar.spec`, установщика — `packaging/installer.iss`. Скрипт проверяет коды завершения и наличие exe/installer.

Результат `dist/artifacts`: установщик, portable ZIP, SHA256SUMS.txt, список установленных зависимостей, сведения о сборке. CI добавляет distribution-check.json. Это воспроизводимая процедура с фиксированными пакетами, не обещание побайтово идентичных EXE: образ Windows и служебные временные метки могут различаться.

ADR-0001 первоначально предлагал pyside6-deploy/Nuitka. Для проверяемой поставки 0.11.0 выбран PyInstaller one-folder: он не требует C++-компилятора, сохраняет Qt DLL отдельными файлами и позволяет испытать один и тот же комплект как portable и установщик. Qt/SQLite/CalDAV и формат пользовательской базы остаются прежними.
