# Windows-дистрибутив — v1.0.1

## Установка и переход с Python

1. Закрой Director Calendar, включая прежний запуск из папки исходников.
2. Открой [GitHub Releases](https://github.com/payuktv/director-calendar/releases), выбери нужную версию и скачай установщик из Assets. Автоматические архивы Source code не предназначены для установки.
3. Запусти DirectorCalendar-1.0.1-Setup-x64.exe от своего обычного пользователя. Python, PowerShell и права администратора для работы приложения не нужны.
4. Открой ярлык Director Calendar. Установщик обновляет одноимённый ярлык рабочего стола и добавляет ярлык меню «Пуск».
5. Проверь привычные события, историю и настройки. Если использовалась стандартная папка данных, ничего переносить не надо.

Файлы программы: `%LOCALAPPDATA%\Programs\DirectorCalendar`.
Данные: `%LOCALAPPDATA%\DirectorControl\director_control.db`.
Это разные папки. Установка/обновление/удаление программы не удаляют базу и резервные копии. Пароль хранится отдельно в Windows Credential Manager с прежним именем сервиса `DirectorControl.CalDAV` и прежним ключом календаря.

Если раньше использовался `DIRECTOR_CONTROL_DATA_DIR`, сохрани эту переменную окружения для нового запуска: нестандартная база автоматически не угадывается. При смене Windows-пользователя/ПК пароль Vault не переносится вместе с SQLite; его нужно ввести заново.

## Обновление

Закрой приложение, запусти установщик следующей версии и открой прежний ярлык. Автоматического скачивания обновлений пока нет. Скачивай комплект из Releases своего приватного репозитория. Публикация происходит после тестов Windows/Linux и проверки дистрибутива одного коммита. [Процедура выпуска](RELEASING.md).

Перед первым открытием существующей базы другой версией приложение под блокировкой одного экземпляра проверяет её и создаёт `backups/before-update-*.db`. Только после успешной копии допускаются инициализация/миграции. Если места нет или копия не проходит проверку, запуск останавливается; исходная база не заменяется. После успешного создания окна сохраняется номер версии в настройках. Повторные запуски той же версии не создают повторных копий обновления. Страховочные копии не удаляются автоматической ротацией.

Установщик блокирует установку/удаление при работающей версии 0.11.0+; старая 0.10.0 ещё не создаёт installer mutex, поэтому перед первой установкой обязательно закрыть её вручную. Имеющаяся блокировка БД по-прежнему защищает от двух экземпляров, включая запуск из исходников.

Понижение установленной версии блокируется. Новая программа также отказывается открывать базу с более новым сохранённым номером приложения. Это не защита от запуска старого исходного кода, не знающего этого правила. Для аварийного возврата используй проверенную резервную копию и соответствующую ей версию, сохранив отдельно актуальную базу. Автоматический откат приложения/базы не реализован.

## Переносимая поставка

Распакуй **весь** `DirectorCalendar-1.0.1-portable-x64.zip`, сохрани рядом `DirectorCalendar.exe` и каталог `_internal`. Запусти exe; при необходимости создай ярлык из настроек приложения. Данные всё равно хранятся в AppData, а не рядом с exe. Для обновления распакуй новую версию в отдельную папку и обнови ярлык. Не копируй только exe и не накладывай разные версии `_internal` вручную.

## Что проверяет CI

- Реальная сборка оконного exe с включёнными Python/Qt, иконкой, tzdata, сертификатами TLS и Windows Vault backend.
- Скачивание настоящего опубликованного установщика предыдущей версии с проверкой размера, SHA-256 и манифеста. Исходники её зафиксированного коммита используются для подготовки тестовых данных.
- Создание синтетических данных старым Store, запуск старого установленного exe, установка нового поверх него и повторный запуск.
- Сравнение таблиц событий, исходного плана, факта, истории, категорий, настроек; только служебные отметки версии/автокопии могут изменяться.
- Страховочная копия перед первым новым запуском; отсутствие дублирования при переустановке.
- Сохранение синтетического пароля в Windows Vault.
- Путь с кириллицей, пробелами, апострофом и `&`; запуск из сторонней папки, без Python в PATH/PYTHONPATH/PYTHONHOME.
- Блокировка обновления работающего приложения и downgrade; сохранность базы/копий/Vault после удаления и новой установки.
- Диагностика самого bundle: GUI, iCalendar, часовой пояс, CA bundle, Vault, backup/restore и путь ярлыка.

`--verify-installation <result.json>` — явная диагностическая команда для разработчика. Она использует временную синтетическую базу, отдельную временную запись Vault и не открывает рабочий календарь. Сетевого доступа к Mail.ru нет.

Hosted Windows runner всё ещё содержит установленный Python, но дочернему exe недоступны пути к нему. Кандидат v0.13.10 также прошёл приёмку на Windows 10 x64 пользователя: с чистым профилем данных приложения, без путей среды разработки и с реальной синхронизацией Mail.ru. Это не проверка на заново установленной Windows; точные результаты и ограничения приведены в [протоколе приёмки](ACCEPTANCE-v1.0.0.md). v1.0.0 выпускает принятую функциональность как стабильную. Дистрибутив пока не подписан Authenticode; сертификат подписи не настроен.

## Воспроизводимая процедура сборки

Windows x64, Python 3.14.10 x64, MSVC C++ build tools и Inno Setup **6**:

```powershell
./scripts/build_windows.ps1
```

Зависимости runtime и сборки закреплены точными версиями в `packaging/requirements-windows.lock`; установка идёт без автоматического выбора транзитивных зависимостей, затем `pip check` проверяет полноту. Для приложения достаточно PySide6 Essentials: Addons, PDF и WebEngine не устанавливаются. `.build-venv` отделён от рабочего окружения `.venv` и пересоздаётся при изменении lock-файла, чтобы исключённые пакеты и плагины не попадали в новую сборку. Конфигурация PyInstaller — `packaging/director-calendar.spec`, установщика — `packaging/installer.iss`. Скрипт проверяет коды завершения и наличие exe/installer, записывает размеры комплекта, установщика и ZIP в `build-info.txt` и сводку CI.

Результат `dist/artifacts`: установщик, portable ZIP, SHA256SUMS.txt, список установленных зависимостей, сведения о сборке. CI добавляет distribution-check.json и upgrade-source.json. Перед публикацией Release добавляет release-manifest.json и контрольные суммы всех вложений, кроме самого файла контрольных сумм. Это воспроизводимая процедура с фиксированными пакетами, не обещание побайтово идентичных EXE: образ Windows и служебные временные метки могут различаться.

ADR-0001 первоначально предлагал pyside6-deploy/Nuitka. Для проверяемой поставки 0.11.0 выбран PyInstaller one-folder: он сохраняет Qt DLL отдельными файлами и позволяет испытать один и тот же комплект как portable и установщик. Начиная с 0.13.9, подготовка исправленных XML-модулей требует MSVC; пользователю установленного приложения компилятор не нужен.

## Аварийное восстановление (0.12.0)

При ошибке проверки базы на старте можно выбрать исправную резервную копию. После подтверждения исходные файлы сохраняются в recovery рядом с базой, копия проверяется и подготавливается отдельно. При ошибке подготовки или сохранения исходников замена не выполняется. После успеха открой приложение снова. Копии более новой версии отвергаются.

## Журнал ошибок

Открой **Настройки → Диагностика**, чтобы перейти к папке журнала или скопировать путь. По умолчанию журнал находится в `%LOCALAPPDATA%\DirectorControl\logs\director-calendar.log`; сохраняются текущий файл и три предыдущих, примерно по 1 МиБ каждый. Записываются операция, тип ошибки и место в коде. Тексты исключений, пароли, адреса CalDAV и содержимое календаря не записываются; автоматической отправки журнала нет. При недоступности папки приложение продолжает работать, а раздел диагностики показывает, что запись недоступна.

## SQLite и очистка обновлений

Windows-комплект использует официальную SQLite 3.54.1 x64 вместо DLL из стандартной поставки Python. `scripts/prepare_sqlite.py` проверяет закреплённый SHA3-256 архива и source ID в отдельном процессе; системный Python не меняется. Windows-тесты используют приватную копию расширения Python рядом с новой DLL. PyInstaller заменяет единственный экземпляр sqlite3.dll, а проверка готового EXE и публикация требуют точную версию/source ID. `build-info.txt` сохраняет URL и контрольные суммы.

`packaging/retired-files.iss` содержит точные имена ранее поставлявшихся файлов. Установщик удаляет только эти файлы и отклоняет пути с reparse points до начала обновления. Каталоги данных и произвольные пользовательские файлы не очищаются. При изменениях зависимостей обновляйте этот список: CI сравнивает хеши всех установленных файлов с новым комплектом после обновления и повторной установки, дополнительно проверяет исторические остатки и сохранность посторонних файлов.

Восстановление принимает только схемы, создаваемые приложением, включая поддерживаемые старые версии. Посторонние SQL-объекты и изменения определений таблиц отклоняются до миграции. Лимиты: база с журналами — 512 МиБ, значение/строка — 8 МиБ, проверка — 15 секунд, копирование — 30 секунд. При отказе используйте исходную совместимую копию; ручная правка SQL-схемы не поддерживается.

С версии 0.13.9 проверяются также реальные типы и допустимые значения записей: имена, названия, комментарии, идентификаторы, числовые флаги и допуски, даты и метаданные синхронизации. JSON истории ограничен глубиной 32 и 100000 значениями; прежние текстовые описания поддерживаются. Некорректная копия отклоняется до замены рабочей базы, а подготовленный файл проверяется повторно. Ошибка создания окна тоже оставляет доступ к диалогу аварийного восстановления.

## Expat 2.10.0

`scripts/prepare_expat.py` скачивает официальные архивы CPython 3.14.10 и Expat 2.10.0 с проверкой закреплённых SHA-256, собирает вместе `pyexpat` и `_elementtree`, затем выполняет upstream-наборы `test_pyexpat`, `test_xml_etree`, `test_xml_etree_c`. Разные версии этой пары несовместимы, поэтому замена одного модуля запрещена. Системный Python не меняется. Оба CI-набора используют приватный overlay; PyInstaller заменяет оба модуля, а готовый EXE проверяет версию, C-ускоритель, Unicode/пространства имён, запрет DTD и исправленный случай пустого подпарсера. В комплект входят лицензии, в build-info — источники и хеши. Публикация требует `xml_runtime_verified` и `backup_records_validated`.
